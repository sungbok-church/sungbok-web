# 관리자(`/admin`) 설계 — 기반 + 1차 콘텐츠

**상태**: 승인(2026-11-17). DB 구조는 `supabase/schemas/schema.sql` 로 옮겼다(2026-11-19, ADR 0019). 패키지 A(기반) 끝 — 운영 반영(2026-11-24). 그 사이 사용자 결정으로 바뀐 화면 표준(글자 덜기 · 검색 줄 · 상세 «더 보기» · 단계형 등록 · 브라우저 뼈대 · 미리 받기)을 6.10 에 반영했다(2026-11-24). 지금 있는 것의 세부는 [domains/admin.md](../domains/admin.md). DNS·메일 발송 설정은 사용자가 따로 알아본다(12절)
**날짜**: 2026-11-17
**앞선 결정**: [ADR 0008](../decisions/0008-admin-backend-vercel-supabase.md)(Vercel + Supabase, 같은 앱 `/admin`) · [ADR 0012](../decisions/0012-date-temporal-and-admin-libraries.md)(날짜·라이브러리) · [ADR 0014](../decisions/0014-content-repository-and-video-id-link.md)(저장소 계층·영상 id 연결)

이 문서는 관리자 전체의 구조를 정한다. 구현은 9절의 작업 패키지 순서로 나누고, 패키지마다 구현 계획을 따로 쓴다.

## 1. 목적

교회 사람이 **개발자 없이** 다음을 할 수 있게 한다.

- 매주 올라오는 내용(주보·주일광고·성복의 뜰·교회앨범·설교 시트지)을 등록하고 고친다. 지금은 기존 사이트 글을 한 번 옮겨 둔 상태라, 새 글은 개발자가 다시 옮겨야 한다.
- 새가족 등록·문의를 받는다(지금 «보내기» 는 아무것도 전송하지 않는다).
- 누가 무엇을 할 수 있는지(그룹·권한)를 바꾸고, 메뉴를 켜고 끈다.
- 누가 언제 무엇을 바꿨는지 확인한다.

오픈 목표는 2027-01(회의록 D14)이고, 이 사이트는 나중에 교회 쪽에 넘길 수 있어야 한다(ADR 0008).

## 2. 목표 · 하지 않는 것 · 실패로 보는 것

**목표**

1. PC와 휴대폰 둘 다에서 로그인해 같은 일을 할 수 있다(반응형).
2. 사용자 그룹을 만들고, 그룹마다 메뉴와 그 화면의 기능(조회·등록·수정·삭제·완전 삭제·엑셀 다운로드·이력조회)을 따로 허용한다.
3. 관리자 메뉴와 홈페이지 메뉴를 화면에서 켜고 끄고, 이름과 순서를 바꾼다.
4. 사람이 정하는 분류는 코드관리 화면에서 관리한다.
5. 모든 변경을 칸 단위(변경 전 → 변경 후)로 남긴다.
6. 삭제는 대상에 따라 휴지통(복구 가능)과 완전 삭제를 구분한다.
7. 저장하면 공개 사이트에 바로 반영된다.
8. 홈 히어로를 사진 · 유튜브 영상 중에서 골라 바꾼다.
9. 다음세대 부서 페이지의 소개 글 · 담당자 · 사진을 부서별로 바꾼다.
10. 파일은 공통 표 둘(묶음 · 파일)로 관리하고 모든 화면이 같이 쓴다.

**하지 않는 것(이번 범위 밖)**

- 2차 대상: 행사 포스터(기간), 긴급 공지 띠, 섬기는 이들, 예배 시간표(부서 예배의 요일 · 시간 · 장소 포함).
- 홈 히어로에 영상 파일 올리기(사용자 결정) — 내려받기 용량 때문에 영상은 유튜브로만 한다(6.12).
- 보류: 일정 캘린더, 헌금 안내, 기도 요청, 선교 소식, 연혁.
- 화면에서 새 메뉴 만들기 — 메뉴 하나는 화면 코드 하나라 배포가 필요하다.
- 올린 글의 승인 절차 — 권한이 있는 사람이 공개로 저장하면 바로 공개된다.
- 교인 로그인, 자유게시판, 결제.
- 설교 영상 등록 — 유튜브 재생목록에서 자동으로 온다.
- 백업(사용자 결정) — 따로 만들지 않고, 나중에 Supabase Pro 요금제의 자동 백업을 쓴다. 그때까지 관리자에서 새로 올린 내용의 사본은 Supabase 에만 있다. 기존 사이트에서 옮긴 내용은 시드와 `public/files` 를 지워도 git 기록에 남는다.

**실패로 보는 것(동작하더라도)**

- Supabase 가 멈추거나 느릴 때 공개 사이트가 깨진다.
- 권한을 화면의 버튼 숨김으로만 막는다(주소를 직접 치거나 API 를 직접 부르면 된다).
- 방문자 번들에 관리자 전용 라이브러리가 실린다.
- 새가족의 개인정보가 파기 뒤에도 이력에 남는다.
- 일상적인 쓰기를 만능 키(secret key)로 한다 — 권한 검사를 건너뛰고, 누가 했는지 남지 않는다.

## 3. 제약

- **기존 결정**: 같은 앱 `/admin`, TypeScript(Server Action · Route Handler), zod + TanStack Form(ADR 0017 — 처음에는 react-hook-form) + `@tanstack/react-table`, 시각은 UTC 로 주고받고 표시할 때만 `Asia/Seoul`, 관리자 영역(`src/app/admin/**` · `src/domains/admin/**`)에서는 Temporal 허용.
- **Next 16.4.5**: 학습 자료와 다른 부분이 있다 — 코드를 쓰기 전에 `node_modules/next/dist/docs/` 의 해당 문서를 읽는다(`AGENTS.md`). 미들웨어는 `proxy.ts` 다.
- **Vercel Hobby**: 서버로 보내는 요청 본문 4.5MB 제한, 예약 실행(cron)은 하루 한 번. 리전 서울.
- **Supabase 무료**: DB 500MB · Storage 1GB · 프로젝트 2개 · 1주일 DB 활동이 없으면 정지. 사용할 프로젝트는 사용자가 지정했다(주소·ref 는 문서에 적지 않는다 — 환경변수와 Secret 에만 둔다). **지금은 사용자 개인 계정의 프로젝트**이고, 교회 명의 계정을 받으면 그쪽으로 옮긴다(ADR 0008 의 «교회 명의» 는 그때 맞춘다) — 그래서 DB 구조·권한·초기 행은 전부 변경 파일에 있어야 하고, 프로젝트 주소가 코드에 박히면 안 된다(환경변수로만). 나중에 Pro 요금제로 올릴 수 있다(정지 없음 · 자동 백업).
- **공개 레포**: 키를 커밋하지 않는다. 환경변수의 정본은 GitHub Secrets 이고 수동 워크플로우로 Vercel 에 넣는다([deploy-and-env.md](../workflow/deploy-and-env.md)). production 과 preview 에 같은 값이 들어간다 — preview 배포도 운영 DB 를 본다.
- **디자인 시스템**: 관리자는 shadcn admin 의 부품·배치·크기·모션을 원본 그대로 쓰고 색만 이 사이트 팔레트로 바꾼다(ADR 0016 — 처음에는 «더 촘촘하게, 연출 모션 없음, 터치 44px, 한글 최소 13px» 였으나 2026-11-18 사용자 결정으로 바뀌었다). 공용 부품(`ResponsiveList` · `form-field` · `image-dropzone` · `table` · `sheet` · `dialog` · `sonner`)을 쓴다([design-system.md](../design/design-system.md)).
- **접속 시점 이미지 변환을 쓰지 않는다**([ADR 0013](../decisions/0013-photo-size-variants-prebuilt.md)) — 올릴 때 필요한 크기를 만들어 저장한다.
- **TDD**: 로직 모듈(camelCase `.ts` · `use*` 훅)은 실패하는 테스트를 먼저 쓴다. 화면 부품은 강제하지 않는다.
- **공개 화면의 주소는 바뀌지 않는다**: 기존 글의 id 를 그대로 옮긴다 — 주일광고·성복의 뜰·시트지는 «게시판-글번호»(`0401-147`), 주보는 주일 날짜(`2026-11-15`), 앨범은 번호. 주보의 공개 주소는 이 id(날짜)로, 주일광고·성복의 뜰의 공개 주소는 영상 id 로 찾는다.

## 4. 접근 비교

**권한과 메뉴**

| 안 | 내용 | 결과 |
|---|---|---|
| A. 고정 역할 | 사무 담당·부서 담당자를 코드에 둔다(ADR 0008 의 원래 안) | 탈락 — 역할이 바뀔 때마다 개발자가 필요하다 |
| B. 그룹·권한만 DB | 메뉴와 기능 목록은 코드, 그룹과 그룹별 권한은 DB | 탈락 — 운영 중에 메뉴를 빼려면 배포해야 한다(사용자 지적) |
| C. 메뉴를 화면에서 만들기까지 | 메뉴 트리 전체를 화면에서 추가·삭제 | 탈락 — 화면 없는 메뉴가 생긴다. 새 메뉴는 어차피 화면 개발이 필요하다 |
| **D. 메뉴는 데이터, 추가만 배포** | 메뉴 행은 DB 변경 파일로 들어가고, 화면에서는 사용 여부·이름·순서만 바꾼다. 그룹·권한은 화면에서 관리 | **채택(사용자 결정)** |

**그 밖의 선택**

| 무엇 | 탈락한 안 | 채택 |
|---|---|---|
| 화면 UI | 공개 템플릿(Kiranism starter, Studio Admin 등)을 통째로 들이기 — 자기 테마와 의존성(Clerk · Zustand)이 따라오고 디자인 시스템과 겹친다 | `next-shadcn-dashboard-starter` 를 참고한다(사용자 결정, 2026-11-18 — ADR 0016 · 0017): shadcn 의 부품(`sidebar` 등)과 배치·크기·모션을 원본 그대로 쓰고 색만 이 사이트 팔레트로 바꾼다. 구조와 화면 패턴을 가져오고 저장소를 통째로 들이지는 않는다(Clerk · Sentry · Base UI 부품 제외) |
| 이력 기록 | 화면 코드가 저장할 때마다 이력을 쓴다 — 빠뜨리는 곳이 생긴다 | DB 트리거 하나를 모든 표에 붙인다 |
| 파일 올리기 | 서버를 거쳐 올린다 — 4.5MB 제한에 걸린다 | 브라우저에서 줄여 Storage 로 직접 올린다 |
| 화면 그리기 | 페이지 전체를 클라이언트로 | 서버 컴포넌트가 기본, 상호작용 조각만 클라이언트 |

## 5. 사용자가 정한 것

대화에서 사용자가 직접 정한 것이다. 바꾸려면 사용자에게 다시 묻는다.

- PC·휴대폰 둘 다 지원한다(홈페이지처럼 반응형).
- 사용자 그룹 + 메뉴 권한 + 화면별 기능 권한(엑셀 다운로드·이력조회·등록·수정·삭제 등)을 둔다.
- 메뉴는 데이터로 관리한다 — 관리자 메뉴와 홈페이지 메뉴 둘 다. 화면에서 새 메뉴를 추가하지는 않고, 이름 바꾸기는 한다.
- 프로그램이 분기하는 값은 enum(값은 영문 대문자), 콘텐츠를 나누는 이름은 분류(categories), 관리자가 바꾸는 값과 enum 의 화면 이름은 공통코드(codes, 영문 대문자)다 — [ADR 0020](../decisions/0020-codes-uppercase-and-categories-split.md)(2026-11-20).
- 표마다 등록일·수정일·삭제일을 두고, 휴지통으로 갈 것과 완전히 지울 것을 구분한다.
- 이력은 칸 단위로 변경 전 → 변경 후를 남긴다.
- 새가족 등록은 자체 폼이다(DB 저장 + 담당자 알림). 네이버 폼은 쓰지 않는다.
- 화면은 서버 컴포넌트 + 필요한 부분만 클라이언트로 그린다.
- 관리자 화면은 `next-shadcn-dashboard-starter`(Next.js 용 shadcn 관리자 스타터)를 참고해 만들고, 색 같은 것은 이 사이트 것에 맞춘다(2026-11-18, [ADR 0017](../decisions/0017-admin-reference-next-starter-and-tanstack-form.md)). 폼은 TanStack Form. 모션·글자 크기·터치 영역·좁은 화면 기준은 shadcn 원본 그대로다([ADR 0016](../decisions/0016-admin-ui-follows-shadcn.md)).
- Supabase 는 사용자가 지정한 프로젝트를 쓴다.
- 홈 히어로는 사진 · 유튜브 영상 주소 중에서 설정한다. 영상 파일 올리기는 넣지 않는다(2026-11-17).
- 다음세대 부서 페이지의 사진 · 소개 글 · 담당자 · 담당자 사진을 관리자에서 바꾼다. 지금 값(샘플 포함)을 DB 에 넣고 시작하고, 코드에 박아 두지 않는다(2026-11-17).
- 파일은 공통 표 둘(묶음 · 파일)로 관리하고 모든 화면이 같이 쓴다(2026-11-17).
- 로컬 개발은 podman 을 쓴다.

## 6. 구조

### 6.1 기술 구성

| 무엇 | 선택 |
|---|---|
| DB·로그인·파일 | Supabase(Postgres · Auth · Storage). 접근은 `@supabase/supabase-js` + `@supabase/ssr` |
| DB 구조 | 정본 `supabase/schemas/schema.sql`(구조) · `supabase/reference.sql`(초기 행)을 고치고 `pnpm db:sync` 가 `supabase/migrations/` 의 변경 파일을 만든다(손으로 쓰지 않는다 — ADR 0019, 대시보드에서 손으로 만들지 않는다). TS 타입은 여기서 자동 생성. 운영 DB 에는 수동 GitHub Actions 워크플로우로 적용한다(환경변수 동기화와 같은 방식 — 넘겨받는 사람도 같은 절차). preview 도 운영 DB 를 보므로 변경 파일은 **코드보다 먼저** 적용하고, 먼저 적용해도 지금 코드가 깨지지 않게 «추가 → 코드 배포 → 제거» 순서로 쓴다(ADR 0008) |
| 읽기(관리자) | 서버 컴포넌트가 로그인한 사람의 세션으로 조회. 목록의 검색·필터·정렬·페이지는 주소 쿼리에 두고 서버가 다시 조회 |
| 쓰기 | Server Action: zod 검증 → 권한 확인 → DB(로그인한 사람의 세션, RLS 가 다시 막는다) → 공개 화면 갱신 |
| 읽기(공개) | 저장소 계층의 `load` 를 서버 전용 DB 조회로 교체. 서버에서만 조회하고(공개 화면 브라우저에는 Supabase 클라이언트를 싣지 않는다) 태그를 붙여 캐시 |
| 폼 | TanStack Form + zod(화면과 Server Action 이 같은 스키마) — ADR 0017 |
| 목록 | `@tanstack/react-table` + `ResponsiveList`(`md` 이상 표, 그 아래 카드) |
| 로그인 검사 | `proxy.ts` 를 `/admin/*` 에만 건다 — 공개 페이지의 정적 생성을 건드리지 않는다. 서버에서 사용자 확인은 Supabase 공식 안내의 `getClaims()` 방식 |

만능 키(secret key)는 네 곳에서만 쓴다: 계정 만들기·비밀번호 초기화, 예약 작업(6.9), 기존 자료 가져오기 스크립트(7절), 새가족 접수 받기(6.11 — 방문자는 로그인이 없다). 네 곳 모두 서버 전용 파일(`*.server.ts` + `server-only`)에 두고, 그 밖의 쓰기는 전부 로그인한 사람의 세션으로 한다.

### 6.2 폴더

```
supabase/schemas/schema.sql     DB 구조·권한·트리거(정본)
supabase/reference.sql          초기 행(메뉴·그룹·코드, 정본)
supabase/migrations/            db:sync 가 만든 변경 파일(운영 적용용)
src/app/(site)/…                지금의 공개 라우트 전부(주소는 그대로, 폴더만 묶음)
```

- 지금 `src/app/layout.tsx` 는 공개 사이트의 헤더·푸터·부드러운 스크롤을 전부 감싼다. 관리자에는 이것들이 나오면 안 되므로 공개 라우트를 `(site)` 묶음으로 옮기고 레이아웃을 둘로 나눈다. 주소는 바뀌지 않는다.
- 공개 쪽(`src/domains/*`(admin 제외), `src/app/(site)/**`)에서 `src/domains/admin/**` 과 관리자 전용 라이브러리(TanStack Form · react-table · `@supabase/ssr` 의 브라우저 클라이언트)를 import 하지 못하게 lint 규칙을 건다(ADR 0008).
- 관리자 화면은 검색에 걸리지 않게 한다(noindex).

### 6.3 표

**표 정의의 정본은 [`supabase/schemas/schema.sql`](../../supabase/schemas/schema.sql)** 이고 초기 행은 [`supabase/reference.sql`](../../supabase/reference.sql) 이다([ADR 0019](../decisions/0019-db-schema-ssot-uuid-v7.md), 2026-11-19). 칸 · 인덱스 · 권한 규칙은 거기서만 고친다 — 이 문서에 표 목록을 다시 적지 않는다(두 곳이 어긋나지 않게). 여기에는 구조의 큰 줄기만 둔다.

| 묶음 | 표 |
|---|---|
| 사용자 · 권한 · 메뉴 | `profiles`(= 로그인 계정 id) · `groups` · `user_groups` · `menus` · `group_permissions` |
| 분류 | `category_groups`(묶음, reference.sql 로만) · `categories` |
| 공통코드 | `code_groups`(묶음 · 잠김, reference.sql 로만) · `codes` |
| 파일(공통) | `file_lists`(묶음) · `files` — 모든 화면이 이 두 표만 쓴다(사용자 결정) |
| 콘텐츠(휴지통 있음) | `bulletins` · `news_videos` · `albums` · `resources` ─< `resource_videos` |
| 사이트 화면 | `home_hero`(한 줄) · `departments`(8줄) ─< `department_staff` |
| 새가족 · 이력 | `newcomers` · `submission_attempts`(접수 횟수 제한) · `audit_log` |

- **id 는 uuid v7**(`private.uuid_v7()` — Postgres 18 이 Supabase 에 열리면 내장 함수로 바꾼다). 예외: 이력 · 횟수 제한은 숫자, 연결 표는 두 칸 키, 코드 묶음은 key.
- **공개 주소는 id 와 따로 둔다**: 주보 = 날짜, 주일광고 · 성복의 뜰 = 영상 id, 앨범 · 시트지 = `slug`(기존 글은 기존 번호, 새 글은 시퀀스 — 앨범은 1000 부터). 주일광고 · 성복의 뜰의 기존 글번호는 `legacy_id`(다시 가져오기의 같은 글 판정).
- **공통 칸**: `created_*` · `updated_*`, 휴지통이 있는 콘텐츠 5종만 `deleted_*`. 값은 트리거(`private.stamp`)가 로그인한 사람으로 채운다. 사용자 · 그룹 · 코드 · 메뉴는 지우지 않고 끄므로(`is_active`) `deleted_*` 가 없다.
- **달력 날짜는 `date`**(주보 · 설교 · 방문 예정일), 순간은 `timestamptz`.
- **분류 칸은 (묶음 key, 분류 id) 두 칸 외래 키** — 앨범에 주일광고 분류가 들어가지 못한다. 분류 묶음: 주일광고 분류 · 성복의 뜰 분류 · 앨범 분류 · 주일 강해 · 시리즈 · 가정/명절/절기. 공통코드 묶음: 직분 · 콘텐츠 상태 · 새가족 구분 · 새가족 처리 상태(뒤 셋은 enum 과 같은 값이라 잠김).
- **글은 파일을 직접 가리키지 않고 항상 묶음을 가리킨다**(`…_list_id`, 칸마다 유일 — 한 묶음은 한 자리에만). 한 장짜리 자리도 한 개만 든 묶음이다. 묶음이 어느 글의 어느 자리에 붙었는지는 뷰 `private.file_list_owners` 가 모은다 — 권한 판정과 «주인 없는 묶음» 정리가 이 뷰를 쓴다. `*_list_id` 칸을 새로 만들면 이 뷰에 넣어야 하고, 빠지면 `pnpm db:test` 가 실패한다.
- `files.variants` 는 폭별로 미리 만든 파일 목록(`[[가로 px, 경로], …]`)이다. Storage 경로는 `<메뉴 key>/<묶음 id>/<파일 id>.<확장자>` — 한글 원래 이름은 `original_name` 에만.
- 같은 Storage 파일을 여러 `files` 행이 가리킬 수 있다(부서 샘플 사진). 실제 파일은 가리키는 행이 하나도 남지 않았을 때 지운다.
- «같은 주일의 주보는 하나» 같은 유일 규칙은 삭제된 행을 빼고 검사한다(부분 유일 인덱스).
- **새가족**: 동의한 시각과 동의 문구의 판(`consent_version`)을 남긴다.
- **`profiles.email`** 은 로그인 계정의 사본이고 트리거가 맞춘다(화면에서 못 바꾼다). 로그인 계정은 지울 수 없다(`on delete restrict`) — 끈다.
- **동시 수정**: 저장할 때 화면이 열었던 `updated_at` 을 함께 보내 같을 때만 고친다. 0줄이면 «다른 사람이 먼저 고쳤습니다».

### 6.4 권한

- 권한 하나는 «메뉴 + 기능» 이다(예: 주보 + 수정). 그룹이 권한을 갖고, 사용자는 그룹에 속한다. 여러 그룹에 속하면 합친다.
- DB 함수 `has_permission(메뉴 key, 기능)` 하나가 판정한다: 사용자가 활성이고, 속한 활성 그룹 중 하나가 그 권한을 갖고, 그 메뉴가 사용 중일 때 참.
- **막는 곳은 세 겹이다.** ① DB 행 권한(RLS)이 `has_permission` 으로 막는다 — 마지막 벽. ② Server Action 과 페이지가 시작할 때 같은 판정을 한 번 더 해서 알맞은 안내를 낸다. ③ 화면은 권한 없는 메뉴와 버튼을 그리지 않는다. ③ 만으로는 권한이 아니다.
- 메뉴가 가진 기능 목록(`menus.actions`)은 화면 코드가 정하는 값이라 DB 변경 파일로만 들어간다. 권한 화면(그룹 × 기능 표)은 이 목록을 읽어 그린다.
- 조회 권한이 없으면 그 메뉴가 보이지 않고 주소를 직접 쳐도 막힌다.
- **잠김 방지**: `is_system` 그룹 «전체 관리» 는 모든 권한을 가진 것으로 판정하고, 지우거나 비활성으로 만들 수 없으며, 활성 사용자가 한 명 이상 남아 있어야 한다. 사용자·그룹·메뉴 관리 메뉴는 끌 수 없다(`is_locked`).
- **역할과 권한 올리기 방지**(DB 에서 막는다, 2026-11-23 결정 — 단순화):
  - ① **«전체 관리»**(시스템 그룹 구성원)만: 그룹 만들기, 그룹 고치기(이름 · 설명 · 권한 표 · 끄기 · 켜기), 누구든 어느 그룹에든 넣고 빼기(«전체 관리» 그룹은 빼고 — 아래), «전체 관리» 구성원을 바꾸기 · 끄기 · 비밀번호 초기화. 그룹 화면의 [새 그룹] · [수정] · 끄기/켜기는 «전체 관리» 에게만 보이고, 그 밖의 사람에게 권한 표는 보기 전용이다(그룹 권한이 있어도).
  - ② **그 밖의 사용자 관리자**(«사용자 수정» 권한)는 **자기가 속한 그룹에만** 사람을 넣고 뺀다. 같은 그룹이면 그 그룹의 권한(꺼진 그룹 · 꺼진 메뉴의 잠자는 권한도)이 나와 같이 살고 같이 자서 내게 없는 권한을 줄 수 없다. 비밀번호 초기화 등 «관리»(`can_manage_user`)는 대상이 속한 그룹이 **모두** 내 그룹일 때만(그룹이 없는 사람도 된다) — 초기화하면 그 계정을 받는 것과 같다. **다른 사람의 사용자 정보(이름 · 부서 · 끄기 · 켜기)를 고치는 것도 같은 기준**(2026-11-23 — `guard_profiles` 가 `can_manage_user` 로 막는다. 꺼진 남의 그룹 사람을 켜면 그 그룹의 권한이 되살아난다) — 남의 그룹에 속한 사람은 상세에 [수정] · 끄기/켜기 · 초기화가 없고 수정 주소는 404, 목록의 일괄 끄기/켜기는 그 사람을 건너뛰고 알린다.
  - ③ **부서 범위**: «전체 관리» 가 아니고 담당 부서가 있는 사람은 다른 사람의 부서를 자기 부서로만 정하고(비우기 = 모든 부서 X) 자기 부서의 사용자만 고치고 · 끄고 · 그룹을 바꾸고 · 관리한다 — 예외 없이(범위 밖 계정을 — 부서가 빈 방금 만든 계정도 — 내 부서로 끌어오지 못한다).
  - ④ 자기 자신의 그룹과 부서 범위는 바꿀 수 없다.
  - ⑤ **계정 만들기**: 부서를 계정과 함께 정한다 — 서버가 Auth API 를 부르기 전에 내 부서인지 · 고른 그룹이 내 그룹인지 확인하고 `user_metadata.department` 로 넘기면, 계정이 생길 때 트리거(`on_auth_user_changed`)가 사용자 정보에 넣는다(생길 때만 — 나중에 metadata 를 바꿔도 부서는 그대로). 그룹 없이 만들면 «사용자 등록» 만으로 되고, 그룹을 넣으려면 «사용자 수정» 도 있어야 한다. 내 그룹이 없는 사용자 관리자도 그룹 없이 계정을 만든다.
  - ⑥ **«전체 관리» 소속은 화면에서 아무도 바꾸지 않는다**(2026-11-23 결정 — «전체 관리» 도. 계정을 빼앗겨도 새 «전체 관리» 를 만들지 못하게): `guard_user_groups` 가 로그인한 세션의 넣기 · 빼기를 막고(««전체 관리» 소속은 화면에서 바꿀 수 없습니다»), 사용자 폼은 그 그룹을 고를 거리로 내지 않는다(이미 속했으면 잠긴 줄). 운영자가 대시보드 SQL 편집기로만 바꾼다([deploy-and-env.md](../workflow/deploy-and-env.md) ««전체 관리» 구성원 넣고 빼기»).
  - 메뉴 켜기 · 끄기도 «전체 관리» 만(켜면 잠자던 권한이 깨어난다 — 6.5).
- **부서 담당자의 «자기 부서만»** 은 기능이 아니라 데이터 범위다. 사용자에게 부서(`profiles.department`)를 지정하면 «다음세대 부서» 에서 그 부서(소개 글 · 담당자 · 사진과 그 파일)만 다룰 수 있다(RLS 가 막는다). 부서가 비어 있으면 모든 부서를 다룬다. 다른 메뉴에는 이 범위가 걸리지 않는다.

### 6.5 메뉴

**공통** — 화면에서 되는 것: 사용 여부, 이름, 같은 상위 메뉴 안에서의 순서. 안 되는 것: 추가, 삭제, 주소 변경, 다른 상위 메뉴로 옮기기. 이름을 바꿔도 `default_label` 은 남아 «기본 이름으로» 되돌릴 수 있다.

**켜기 · 끄기는 «전체 관리» 만**(2026-11-23 결정) — 권한은 메뉴가 켜져 있을 때만 살아 있으므로, 메뉴를 켜고 끄는 것은 권한을 바꾸는 것이다(6.4 ① 을 메뉴 쪽으로 돌아가지 못하게). 이름 · 순서는 메뉴 수정 권한으로 바꾼다. DB 가 막는다(`guard_menus`).

**관리자 메뉴** — 왼쪽 메뉴는 `menus(area = admin)` 중 사용 중이고 조회 권한이 있는 것만 그린다.

**홈페이지 메뉴**

- 어떤 페이지가 있는지는 지금처럼 코드(`siteNav`)가 정본이다(페이지 파일이 있는지 테스트가 잠근다). DB 의 `menus(area = site)` 는 **덮어쓸 값**(사용 여부·이름·순서)만 갖는다. 둘을 합치는 것은 순수 함수 하나다.
- DB 를 읽지 못하면 코드의 기본값으로 그린다 — 메뉴 때문에 사이트가 깨지지 않는다.
- 끈 메뉴: 헤더·휴대폰 메뉴·섹션 탭에서 사라지고, 주소를 직접 치면 없는 페이지(404)가 된다. 하위가 전부 꺼진 상위 메뉴도 사라진다.
- 상위 메뉴 주소(`/about`)는 지금 빌드 때 정한 첫 하위로 넘어간다. 켜져 있는 첫 하위로 넘어가도록 접속 시점 처리로 바꾼다.
- 이름은 헤더·휴대폰 메뉴·페이지 머리·브라우저 제목에 함께 반영된다. 주소(slug)는 바뀌지 않는다.
- **끌 수 없는 메뉴(`is_locked`)**: 홈 화면이 고정 링크로 가리키는 페이지(찾아오시는 길, 예배 > 주일예배, 다음세대 8부서 등 — 구현할 때 홈의 링크를 전부 찾아 목록을 확정한다). 이것들까지 끄려면 홈의 해당 링크·별도 함께 숨겨야 하는데, 그건 이번 범위가 아니다.
- 저장하면 공개 화면의 메뉴가 바로 바뀐다(메뉴 태그 갱신).

### 6.6 삭제 규칙

| 방식 | 대상 | 이유 |
|---|---|---|
| 휴지통(`deleted_at`, 복구 가능) | 주보 · 주일광고 · 성복의 뜰 · 교회앨범 · 설교 시트지 | 실수 복구 |
| 바로 뺌(휴지통 없음) | 묶음에서 뺀 파일 한 개(주보의 쪽 · 부서 사진 · 바꾼 히어로 사진 등), 부서 담당자 한 명 | 글이 아니라 글의 일부다. 뺀 기록은 그 글의 이력에 남고, 실제 파일은 예약 작업이 정리한다 |
| 비활성(`is_active`, 지우지 않음) | 사용자 · 그룹 · 분류 · 공통코드 · 메뉴 | 이력과 글이 참조한다 |
| 완전 삭제 | 새가족 접수(보관 기간이 지난 것, 또는 «완전 삭제» 권한으로 직접), 휴지통에 들어간 지 30일 지난 글과 그 묶음 · 파일, 어느 글에도 붙지 않은 묶음과 파일 | 개인정보는 실제 파기가 의무, Storage 는 1GB |
| 지우지 않음 | 변경 이력 | 추가만 가능(수정·삭제 권한 자체를 두지 않는다) |

- 휴지통은 메뉴를 따로 두지 않고 각 목록의 «삭제된 항목» 필터로 본다.
- 휴지통에 든 글과 임시저장은 공개 화면에 나오지 않는다(RLS 와 저장소 계층 둘 다에서 거른다).
- 딸린 행(글에 붙은 묶음과 그 파일, 시트지의 영상 연결)은 부모와 함께 움직인다 — 따로 휴지통에 가지 않는다.

### 6.7 변경 이력

- 트리거 하나(`audit_row`)를 이력 대상 표 전부에 붙인다. 수정은 **바뀐 칸만** `{칸: {이전값, 새값}}` 으로, 등록은 새 값, 삭제는 지워진 값을 `changes` 에 남긴다. `updated_at` · `updated_by` 는 뺀다.
- 누가 했는지는 로그인 세션에서 읽는다 — 그래서 관리자의 쓰기는 항상 로그인한 사람의 세션으로 한다. 예약 작업처럼 사람이 없는 변경은 «시스템» 으로 남는다.
- **개인정보**: 새가족 표는 이름·연락처·남긴 말·메모의 **값을 남기지 않는다**(어느 칸이 바뀌었는지만). 엑셀 다운로드는 누가 언제 몇 건을 받았는지를 이력에 남긴다 — 화면은 `table_name` · `action` · `changes`(건수)만 넣을 수 있고 «누가 · 언제» 는 DB 기본값이 채운다(위조 방지).
- 딸린 행의 변경(부서 담당자 변경, 그룹 소속 · 권한 칸)은 `audit_log.parent_table` · `parent_id` 로 부모에 묶어 부모 글의 이력에서 함께 보인다. 파일은 묶음(`file_lists`)에 묶여 글의 이력에는 «파일 n개» 로 요약된다(파일 한 줄씩의 이력은 화면에 없다).
- 화면: 글 한 건의 이력은 그 화면의 «변경 이력» 창(30개씩 «더 보기»), 목록만 있는 화면(메뉴 · 분류 · 코드)은 그 표 전체, 새가족 목록은 엑셀 받기 기록. 칸 이름과 코드 값은 한글로 보여 준다(«제목: A → B»). 전체 «변경 이력» 메뉴는 없앴다(2026-11-26) — 완전히 지운 글 · 접수의 이력은 상세가 없어 화면에서 보이지 않는다(DB 에는 남는다).

### 6.8 파일 올리기

모든 화면이 같은 통로를 쓴다.

1. 그림: 브라우저에서 긴 변 2000px 안팎 WebP 로 줄이고 가로·세로를 잰다.
2. PDF: 원본을 올리고, 브라우저에서 쪽마다 그림(WebP, 긴 변 1700px 안팎)을 만들어 미리보기 쪽으로 함께 올린다.
   홈 히어로와 다음세대 부서 사진은 화면 폭별 파일(640 · 960 · 1280 · 1920px 안팎)도 함께 만들어 올리고 `files.variants` 에 적는다 — 접속 시점 변환을 쓰지 않기 때문이다(ADR 0013). 화면은 있는 `pickVariant` 로 고른다.
3. 한글 파일: 원본만 올린다. 미리보기는 그림을 따로 올리거나 없이 둔다(지금 자료실 규칙과 같다).
4. Storage 로 **브라우저에서 직접** 올리고(로그인 세션 + Storage 권한 규칙), 그 자리의 묶음(`file_lists`)에 `files` 한 줄을 적는다. 글은 묶음의 id 를 갖는다. 영상 파일은 받지 않는다.

- 버킷은 공개 읽기 하나. 주소는 DB(`files.path`)에 있고 화면은 거기서 만든다.
- 로그인한 사람은 Storage 에 **올리기만** 한다 — 덮어쓰기 · 지우기 규칙은 두지 않는다. 올리기 묶음은 글에 붙지 않아(저장 때 새 묶음에 같은 경로를 적는다) «등록» 권한으로 열리므로, 열어 두면 «등록» 권한만으로 공개된 글의 파일을 바꾸거나 지울 수 있다(2026-11-25 리뷰). 지우기는 예약 작업이 서버 전용 키로 한다. `files` 행의 경로는 그 묶음 메뉴의 경로(`<메뉴 key>/…`, media 버킷)만 적을 수 있다 — DB 가 막는다.
- 공개 화면의 «내려받기 · 이미지 저장» 은 주소에 `?download=<원래 이름>` 을 붙인다 — Storage 는 사이트와 출처가 달라 `<a download>` 가 무시된다.
- 끌어 놓기, 진행 표시, 순서 바꾸기, 올리다 실패한 파일 다시 올리기를 지원한다.
- 올리기 부품은 하나다 — 자리마다 «몇 개까지 · 어떤 종류 · 폭별 파일을 만들지 · 대체 텍스트를 받을지» 만 다르게 준다.
- 글을 저장하지 않고 나가서 남은 묶음과 파일은 예약 작업이 지운다(6.9).

### 6.9 공개 화면 읽기 · 갱신 · 장애 대비 · 예약 작업

- 공개 화면은 지금처럼 저장소 계층(`resourceRepository` · `newsRepository`)으로만 읽는다. 바뀌는 것은 `load` 뿐이다. 조회는 공개용 키로 하고 RLS 가 «공개 상태 + 삭제 안 됨» 만 내준다.
- 조회 결과는 태그를 붙여 캐시한다. Server Action 이 저장 뒤 해당 태그를 갱신한다 — 갱신 대상(예: 시트지를 고치면 자료실 목록 + 그 시트지 페이지 + 연결된 설교 영상 페이지)은 한 파일에 모아 둔다.
- **장애 대비**: 접속 시점에 DB 를 읽지 못해도 공개 페이지가 오류 화면이 되지 않는다 — 마지막으로 성공한 내용을 계속 보여 주고 서버 로그에 남긴다. 그림·PDF 는 브라우저가 Storage 주소에서 직접 받으므로 Storage 가 멈춘 동안에는 보이지 않는다(글 목록과 페이지는 열린다). 우리 도메인을 거쳐 내보내는 통로는 만들지 않는다 — 정지는 예약 작업으로 막고, 그 밖의 Storage 장애는 받아들인다.
- **예약 작업**(하루 한 번, Vercel Cron 하나): ① DB 를 한 번 읽어 정지를 막는다 ② 휴지통 30일 지난 글과 파일을 지운다 ③ 보관 기간이 지난 새가족 접수를 지운다 ④ 어느 글에도 붙지 않은 지 **8일** 넘은 묶음과 파일을 지운다(쓰던 내용 임시 보관이 7일이라 — 그 안에 «불러오기» 한 글의 올린 파일이 지워져 그림이 깨지지 않게, 2026-11-24 리뷰로 24시간에서 바꿈 — `schema.sql` 에는 패키지 D 에서 반영)(Storage 의 실제 파일은 가리키는 행이 없을 때). 이 주소는 비밀 값을 아는 호출만 받는다. DB 쪽은 서버 전용 키로만 부르는 함수 둘이다: `public.purge_expired()`(①~④의 행 지우기) → `public.orphan_storage_objects()`(어느 `files` 행도 가리키지 않는 Storage 파일 목록 — 앱이 Storage API 로 지운다).

### 6.10 화면

```
/admin/login              로그인
/admin                    첫 화면 — 이번 주 할 일
/admin/<메뉴>              목록
/admin/<메뉴>/new          등록
/admin/<메뉴>/<id>         수정(+ 이력 패널)
```

배치(넓은 화면):

```
┌──────────┬──────────────────────────────────────┐
│ 관리자    │ 주보                     [+ 새 주보]  │
│ 첫 화면   │ 검색 [     ]  연도 [2026▾]  상태 [▾]  │
│ 주보     │ 2026-11-22  2장  임시저장        ⋯   │
│ 주일광고  │ 2026-11-15  4장  공개    김○○    ⋯   │
│ …        │ 2026-11-08  4장  공개    김○○    ⋯   │
└──────────┴──────────────────────────────────────┘
```

- 좁은 화면: 왼쪽 메뉴는 시트로 들어가고, 표는 카드 목록이 된다. 등록·수정 폼은 한 열.
- 목록·등록·수정은 **틀 하나**를 같이 쓴다 — 새 종류를 추가할 때는 칸 정의·스키마·Server Action 만 쓴다.
- 등록·수정: «임시저장» 과 «공개» 를 구분해 저장, 저장하지 않고 나가면 경고, 공개한 뒤 «사이트에서 보기» 링크.
- **화면 흐름 표준(사용자 결정, 2026-11-20)** — 모든 관리 화면은 이 틀을 따른다. 목록만 있는 화면(메뉴 관리 · 코드 관리)도 있다.
  - **글자는 최소(사용자 결정, 2026-11-24 — 관리자 전체)**: 화면 설명 줄 · 카드/칸 아래 안내 문장을 달지 않는다. 상세는 한 값을 한 번만 보인다. 도움말은 실수를 막을 때만(«나중에 바꿀 수 없습니다» 등). 글자 수는 한도의 80% 를 넘겨 쓸 때만. 콘텐츠 화면도 같다.
  - **목록**: 머리(제목 · [새로 만들기] · [엑셀 다운로드]) → 검색 줄 한 줄(검색어 · 조건 · 기간 · 작은 [초기화] — 조건은 고르면 바로, 검색어는 Enter · 휴대폰 «검색», 기간은 [적용]. [검색] 버튼 · 조건 칩은 없다 — 적용된 값은 각 칸에 보인다) → 표(머리를 눌러 정렬 · 줄을 누르면 **상세**로 · 필요한 화면은 체크해서 일괄 처리) → 아래(총 N건 · 쪽당 10/20/50/100 · 쪽 번호).
  - **상세(보기)**: 머리(제목 · [목록] · 이전/다음 · [수정]) + 자주 쓰지 않는 동작(삭제 · 끄기 · 변경 이력 · 비밀번호 초기화 등)은 «더 보기»(⋯) 메뉴 하나로 접는다 + 머리에 없는 값만 짧은 «항목 — 값» 목록 + 딸린 정보 칸 + 맨 아래 수정 시각 · 사람 한 줄. **목록 → 상세 → 수정** 순서로 들어간다(사용자 결정). **콘텐츠 상세(사용자 결정, 2026-11-24)**: 매주 지난 글을 복제해 쓰므로 머리에 [복제해서 새로 쓰기] 와 (공개된 글이면) [사이트에서 보기] 를 두고, 휴지통 보내기 · 변경 이력은 «더 보기» 에(휴지통에 든 글이면 복구 · 완전 삭제).
  - **등록 · 수정**: 화면 전체 폭, 필수 칸 표시(*) · 글자 수, 아래 고정 막대([취소] · [임시저장](콘텐츠) · [미리보기](콘텐츠) · [저장]). 등록 뒤 «상세로» / «계속 등록». **새 사용자 · 새 그룹만 단계로 나눈다**(사용자 결정, 2026-11-24 — 새 사용자: 기본 정보 → 역할(갖게 될 권한 요약) → 확인, 새 그룹: 이름 → 권한 표). 수정 화면은 한 장짜리 폼이다. **콘텐츠 5종의 등록도 한 장 폼**이다(사용자 결정, 2026-11-24 — 칸이 적고 매주 빨리 올려야 한다. 맞게 썼는지는 [미리보기] 로 본다).
  - **화면 이동 속도(2026-11-24)**: 다른 화면으로 가는 순간 브라우저가 본문 자리에 뼈대를 그린다(서버의 `loading.tsx` 는 두지 않는다). 관리자 링크는 손을 올렸을 때만 미리 받는다(`IntentLink` — `next/link` 직접 사용은 lint 가 막는다). 관리자로 로그인했던 브라우저가 공개 페이지를 열면 관리자 서버를 미리 깨우고 자주 쓰는 화면들을 차례로 불러 둔다 — 순서는 `src/shared/config/adminScreens.ts` 한 곳이고, **화면을 새로 만들면 `ADMIN_SCREENS_READY` 에 넣는다**(그래야 깨우기에 들어간다). 세부는 [admin.md](../domains/admin.md) «불러오는 중» · «서버 미리 깨우기».
  - **변경 이력**: 한 건마다 «시각 · 사람 · 동작» 아래 **표(항목 | 이전 | 이후)**(사용자 지적 — 글로 «이전 → 이후» 를 늘어놓지 않는다). 버튼은 그 메뉴의 «이력조회» 권한이 있을 때만(사용자 결정).
  - **엑셀 다운로드는 데이터로 정한다**: 메뉴의 기능 목록(`menus.actions`)에 «엑셀 다운로드» 가 있고 그 권한이 있을 때만 목록에 버튼이 보인다. 실제 내려받기 기능은 새가족에만 만든다(사용자 결정).
  - **목록 편의 기능(사용자 결정 — 권장안 전부)**: 쪽당 개수(마지막 값 기억) · 최근 검색 조건 5개(사용자별 브라우저 보관, 로그아웃 때 지움, **새가족은 보관 안 함**) · 정렬 표시 · 기간 조건 · 상세에서 목록으로 돌아오면 조건 · 쪽 유지 · 줄 체크 일괄 처리 · 불러오는 동안 자리 표시 · `/` 로 검색칸. 보류: 표시할 칸 고르기, 로그아웃 5분 전 알림, 다크 모드.
  - **왼쪽 메뉴 배지**: 처리할 건수(«새가족 3» 등)를 메뉴 옆에 — 숫자는 그 화면이 생길 때(패키지 C).
  - **첫 화면**: 할 일 카드(이번 주 주보 · 주일광고 등록 여부, 처리 안 된 새가족)를 처음부터 자리 잡아 두고 기능이 생기면 숫자를 채운다.
- **콘텐츠 미리보기(사용자 결정, 2026-11-20 — 패키지 B)**: 등록 · 수정 화면의 [미리보기] 를 누르면 **화면 전체를 덮는 창**이 열리고 실제 공개 화면 모양으로 보여 준다. 위쪽 막대에서 PC · 태블릿 · 휴대폰 폭을 바꿔 본다(Drupal responsive preview · DNN page preview 와 같은 방식). **저장하지 않은 지금 값**으로 그리고 서버에 아무것도 남기지 않는다. 창 안은 관리자 주소 아래의 별도 틀(iframe — 폭을 바꾸면 실제 기기처럼 배치가 바뀌게), 로그인한 관리자만, noindex. 실제 공개 주소에서 임시저장 글을 띄우는 방식(draftMode)은 쓰지 않는다(사용자 결정).
- **알림 · 확인(사용자 결정, 2026-11-19)** — shadcn 스킬 권장 부품을 쓴다.
  - 저장할 때 확인 창은 띄우지 않는다. 저장은 되돌릴 수 있고 이력이 남는다.
  - 저장되면 토스트(`toast`)를 띄운다: «저장했습니다» + 공개된 글이면 «사이트에서 보기».
  - 저장에 실패하면 토스트로 알리고, 적은 내용은 그대로 둔다. DB 오류 원문은 보이지 않는다(내부 구조가 드러나지 않게). 동시 수정이면 «다른 사람이 먼저 고쳤습니다».
  - 휴지통 보내기: 확인 창(`alert-dialog`, «30일 안에 복구할 수 있습니다»). 보낸 뒤 토스트에 «되돌리기».
  - 완전 삭제(새가족 포함): 더 강한 확인 창(«되돌릴 수 없습니다», 위험 버튼).
  - 공개 중인 글을 임시저장으로 바꿀 때만 확인 창(«사이트에서 사라집니다»).
- **편의 기능(사용자 결정, 2026-11-19)**
  - **복제해서 새로 쓰기** — 주보 · 주일광고처럼 매주 비슷한 글. 복제본은 항상 임시저장이고, 파일은 묶음을 새로 만들어 같은 Storage 파일을 가리킨다(원본 글을 지워도 복제본이 깨지지 않는다 — 6.3).
  - **쓰던 내용 임시 보관** — 창이 닫히거나 로그인이 끊겨도 다시 열면 복구할지 묻는다. 보안 조건:
    - 브라우저 저장소에 **사용자별로** 둔다.
    - **로그아웃하면 지운다.** 저장에 성공해도 지운다. 7일이 지나면 버린다.
    - 콘텐츠 · 사이트 화면 폼만 대상이다. **새가족 · 사용자(비밀번호) 폼은 보관하지 않는다** — 개인정보가 공용 PC 에 남지 않게.
  - **주소에 목록 상태 남기기** — 검색 · 필터 · 정렬 · 페이지를 주소 쿼리에 둔다. 단, **새가족 목록의 이름 · 연락처 검색어는 주소에 넣지 않는다.** 주소는 브라우저 기록과 서버 로그에 남기 때문이다. 상태 · 기간 · 페이지만 넣는다.
  - 저장 단축키 Ctrl/⌘+S, 칸 옆 오류 표시, 파일 올리는 중에는 저장 막기, 빈 목록의 «첫 글 등록하기» 안내(`Empty`).
  - 여러 개 골라 삭제 · 공개 — 권한은 한 줄씩 같은 규칙(RLS)으로 판정하고, 삭제는 위 확인 창을 거친다.
  - 파일: 끌어 놓기 · 진행 표시 · 실패한 것만 다시 올리기 · 올리기 전 미리보기 · 큰 그림은 자동으로 줄이고 알린다.
  - 명령 팔레트(⌘K) — 권한이 있는 메뉴와 글만 찾는다.
  - 첫 화면의 «이번 주 할 일» 카드에서 바로 등록 화면으로 간다.
  - **오래 쓰지 않으면 로그아웃** — 마지막 활동 뒤 일정 시간(기간은 계획 때 정한다)이 지나면 다시 로그인하게 한다. Supabase 의 세션 만료 설정은 유료 요금제 기능이라(구현 때 공식 문서로 확인), 무료에서는 앱이 마지막 활동 시각으로 판단한다.
  - **넣지 않는다(사용자 결정)**: 이력에서 바로 «이 값으로 되돌리기».
- **보안 헤더(사용자 결정, 2026-11-19)** — 관리자 화면에 CSP(Content-Security-Policy)를 건다. 로그인 쿠키는 `@supabase/ssr` 방식이라 브라우저 스크립트가 읽을 수 있으므로, 남의 스크립트가 실행되는 것(XSS)을 막는 것이 곧 로그인 탈취를 막는 것이다. 스크립트는 이 사이트와 nonce 를 단 것만, 연결은 이 사이트와 Supabase 주소만 허용한다(패키지 A 에서 정했다 — [admin.md](../domains/admin.md) «보안 헤더 · 세션»).
- **세션 길이**: access token(JWT)은 1시간, refresh token 은 **만료가 없다** — 쓸 때마다 새 것으로 바뀌고, 한 번 쓴 토큰은 다음 토큰이 쓰인 뒤에는 거절된다(2026-11-19 로컬 확인). 그래서 로그아웃하지 않으면 세션이 계속 이어진다. «오래 쓰지 않으면 로그아웃» 은 쿠키만 지우지 않고 Supabase 에 로그아웃을 알려 그 세션의 refresh token 을 끊는다.
- 첫 화면: 이번 주 주보·주일광고가 올라왔는지, 처리하지 않은 새가족 접수 건수, Storage 사용량.

### 6.11 새가족

- 홈의 «새가족 등록·문의» 패널(`RegisterPanel`)의 «보내기» 를 Server Action 에 잇는다. 받는 값: 종류(등록/문의) · 이름 · 연락처 · 방문 예정일 · 남기실 말 + **개인정보 수집·이용 동의**(동의해야 보낼 수 있고, 동의한 시각을 남긴다).
- 방문자(로그인 없음)에게는 이 표의 권한을 전혀 주지 않는다 — 읽기도 넣기도 RLS 로 막는다. 공개용 키는 브라우저에 실리므로 넣기를 열어 두면 Server Action 을 건너뛰고 DB 에 직접 넣을 수 있어 스팸 방지가 소용없어진다. 접수는 Server Action 이 검증한 뒤 서버 전용 만능 키로 넣는다(6.1 의 네 번째 예외). 알림 받을 사람 조회도 같은 곳에서 한다.
- 스팸: 숨긴 칸(허니팟) + 서버의 횟수 제한. 문자 입력 검사(CAPTCHA)는 스팸이 실제로 생기면 넣는다.
- 접수되면 «새가족» 메뉴의 조회 권한이 있는 활성 사용자 모두에게 알림 메일을 보낸다(받을 사람: `public.newcomer_notify_emails()`, 서버 전용). 메일에는 **개인정보를 싣지 않고** «새 접수 1건» 과 관리자 화면 링크만 넣는다. 메일이 실패해도 접수는 성공이다 — 접수는 DB 에 있고 첫 화면에 건수가 뜬다.
- 접수함: 상태(새 접수 → 연락함 → 완료) · 메모 · 담당자. 엑셀 다운로드.
- 보관: **접수한 날부터 1년**(사용자 결정)이 지나면 처리 상태와 상관없이 예약 작업이 완전히 지운다(등록·문의 같은 기간). 동의 문구에 같은 기간을 적는다.

### 6.12 홈 히어로

- 종류는 둘 중 하나다: **사진** · **유튜브 영상**(주소를 붙여 넣으면 영상 id 로 바꾼다 — `parseYoutubeVideoId`).
- **영상 파일 올리기는 넣지 않는다(사용자 결정).** 올린 영상은 방문할 때마다 Storage 에서 내려가 내려받기 한도를 쓴다 — 5MB 영상 기준으로 무료 요금제(월 5GB 안팎)는 방문 1,000번쯤, Pro(월 250GB, 넘으면 GB 당 $0.09)는 5만 번쯤에서 찬다. 유튜브는 이 비용이 없다.
- **대표 사진은 어느 종류에서나 필수다.** 영상이 준비되기 전, 좁은 화면(`lg` 미만), «동작 줄이기» · 데이터 절약 설정, 영상을 못 불러온 경우, 그리고 히어로가 사진 띠로 내려앉는 변형 연출에는 대표 사진을 쓴다.
- 영상은 항상 소리 없이 재생한다(회의록 D10 — 진입 시 음악 자동재생 없음).
- 유튜브는 대표 사진을 먼저 보여 주고 첫 화면이 그려진 뒤에 플레이어를 붙인다 — 플레이어가 첫 화면 속도를 늦추지 않게(ADR 0010).
- **지금 히어로 사진을 DB 에 넣고 시작한다.** DB 를 읽지 못하면 마지막으로 성공한 내용을 쓴다(6.9). 그것도 없을 때(첫 빌드에서 실패 등)만 레포에 남겨 둔 사진 한 장으로 그린다 — 장애 대비용이지 설정값이 아니다.
- 화면: 종류 고르기 → 대표 사진 올리기(대체 텍스트 포함) → (유튜브 주소) → 미리보기 → 저장.
- **유튜브 영상이 히어로 안에서 어떻게 보이고 변형 연출과 어떻게 이어지는지는 시안으로 정한다**([prototype-preview.md](../workflow/prototype-preview.md)) — 지금 히어로는 오른쪽 전경 사진이 배경으로 번지고 스크롤하면 사진 띠로 변한다. 유튜브 플레이어는 시작할 때 제목 · 로고가 잠깐 보이는 것을 완전히 없앨 수 없다 — 받아들일 만한지 시안에서 본다.

### 6.13 다음세대 부서

- 부서는 8개로 고정이다(enum — 화면에서 추가·삭제하지 않는다). 부서마다 다음을 고친다.
  - **소개**: 대상 나이 · 사진 위 한 줄 · 소개 글 · 맨 아래 안내 한 줄.
  - **담당자**: 이름 · 직함 · 사진 · 인사말(없을 수 있음), 순서. 0명이면 그 구역을 그리지 않는다.
  - **사진**: 순서가 있고 **첫 장이 도입부 사진**, 나머지가 쇼케이스다(`DepartmentPageProps.photos` 와 같은 규칙). 사진마다 대체 텍스트. 도입부가 사진을 전제로 한 화면이라 최소 한 장은 남긴다.
- **코드에 남는 것**: 부서 이름(홈페이지 메뉴의 이름을 따른다 — 6.5), 예배 요일 · 시간 · 장소(예배 페이지의 시간표와 같은 값이라 2차 «예배 시간표» 때 함께 옮긴다 — 지금 한쪽만 DB 로 옮기면 두 곳이 어긋난다).
- **지금 값으로 시작한다(사용자 결정)**: 지금 `departments.ts` 의 글 · 담당자 · 사진(샘플 포함)을 DB · Storage 에 넣고 → 공개 화면이 저장소 계층으로 DB 에서 읽게 바꾸고 → `departments.ts` 의 값과 더 쓰이지 않는 사진 파일을 레포에서 지운다. 코드에 되돌아갈 기본값(샘플)을 두지 않는다. DB 를 읽지 못할 때는 다른 콘텐츠와 같이 마지막 성공분을 보여 준다(6.9).
- 화면: 부서 고르기 → 소개 · 담당자 · 사진 세 구역. 사진은 격자(끌어서 순서 바꾸기, 첫 장 표시) · 여러 장 올리기 · 대체 텍스트 · 빼기.
- 부서가 지정된 사용자에게는 자기 부서만 보인다(6.4).
- 공개 화면의 사진 부품과 담당자 사진은 지금 레포 사진(`StaticImageData`)만 받는다. 올린 사진(주소 · 크기 · 폭별 파일 목록)을 받도록 바꾼다.
- 홈 화면이 쓰는 부서 컷은 홈의 그림이라 여기서 다루지 않는다.

## 7. 기존 자료 옮기기

- 지금 시드(`bulletinSeed` · `newsVideosSeed` · `albumSeed` · `resourcesSeed`)와 `public/files`(82MB)를 스크립트 한 번으로 DB · Storage 에 옮긴다. id 는 그대로 둔다 — 주소가 유지된다.
- 순서: 표를 만든다 → 옮긴다 → 저장소의 `load` 를 DB 로 바꾼다 → 운영에서 확인한 뒤 시드 파일과 `public/files` 를 지운다. 종류별로 하나씩 한다.
- 옮긴 글의 등록자는 «시스템» 으로 남긴다.
- **다음세대 부서와 홈 히어로도 같은 방식으로 옮긴다**: 지금 코드의 값(부서 글 · 담당자 · 사진, 히어로 사진)을 스크립트로 DB · Storage 에 넣고, 공개 화면을 DB 로 바꾼 뒤 코드의 값을 지운다. 여러 부서가 돌려 쓰는 샘플 사진은 Storage 에 한 번만 올리고 부서마다 `files` 행을 둔다.
- **오픈 전에 한 번 더 가져온다(사용자 결정)**: 관리자가 생기면 그때부터 교회가 관리자에 올리고, 오픈 직전에 개발자가 기존 사이트에서 그 사이 글을 다시 불러온다. 그래서 가져오기는 **기존 사이트를 직접 읽고, 여러 번 돌려도 같은 결과**가 되게 만든다. 기존 사이트를 긁어 온 스크립트는 지금 레포에 없다(작업용 임시 폴더에만 있다) — 레포의 `scripts/` 로 옮긴다.
- **겹칠 때는 관리자에 있는 것이 이긴다**: 이미 있는 글은 건드리지 않는다. 같은 글인지는 주보는 주일 날짜, 주일광고·성복의 뜰은 영상 id, 앨범·시트지는 기존 글번호(없으면 제목 + 날짜)로 본다. 같은 글로 보이지만 확실하지 않은 것은 가져오지 않고 목록으로 보고한다.
- **교회 프로젝트로 옮길 때**: 새 프로젝트에 변경 파일을 적용하고, 표의 내용과 Storage 파일을 옮기고, 환경변수를 바꾼다. **로그인 계정(`auth.users`)도 같은 id 로 옮긴다**(2026-11-19 고침) — 다시 만들면 id 가 바뀌어 `created_by` · 이력의 «누가» · 그룹 소속이 끊긴다. 비밀번호도 함께 옮겨져 다시 발급할 필요가 없다.

## 8. 검증(끝났다고 말하는 기준)

- 권한이 없는 계정으로 주소를 직접 열거나 Server Action · DB 를 직접 불러도 거부된다(권한마다 자동 테스트).
- 로그인하지 않은 채로는 임시저장·휴지통의 글과 새가족 접수를 읽을 수 없다(자동 테스트).
- 주보를 등록 → 공개하면 공개 사이트에 바로 보이고, 삭제하면 사라지며, 복구하면 다시 보인다.
- 글을 고치면 이력에 바뀐 칸만 «이전 → 이후» 로 남고, 고친 사람이 맞다.
- 새가족 접수를 완전히 지운 뒤 DB 어디에도(이력 포함) 이름·연락처가 남지 않는다.
- 메뉴를 끄면 헤더에서 사라지고 그 주소는 404 가 된다. 다시 켜면 돌아온다.
- DB 연결을 끊은 상태에서 공개 페이지가 열린다(메뉴는 기본값, 내용은 마지막 성공분).
- 홈 히어로를 사진 → 유튜브로 바꾸면 홈에 바로 반영되고, 375 폭과 «동작 줄이기» 에서는 어느 종류든 대표 사진만 나온다. 유튜브를 넣어도 홈 첫 화면의 속도 지표가 사진일 때보다 나빠지지 않는다.
- 부서의 소개 글 · 담당자 · 사진을 고치면 그 부서 페이지에 반영되고, 다른 부서가 지정된 계정으로는 바꿀 수 없다(파일을 직접 건드려도 막힌다).
- 부서 데이터를 옮긴 뒤 8부서 페이지가 옮기기 전과 같게 보이고, 코드에 부서 글 · 담당자 · 사진 목록이 남아 있지 않다.
- 글 종류마다 따로 둔 파일 표가 없다 — 파일은 `file_lists` · `files` 두 표에만 있다.
- 방문자 번들에 관리자 전용 라이브러리가 없다.
- 375 · 768 · 1024 · 1280 에서 관리자 화면이 가로로 넘치지 않는다(터치 영역·글자 크기는 shadcn 원본을 따르므로 보지 않는다 — ADR 0016).
- 옮긴 뒤 공개 화면의 글 수가 옮기기 전과 같고(주보 90 · 주일광고 87 · 성복의 뜰 30 · 앨범 4 · 시트지 57), 기존 주소가 그대로 열린다.
- `pnpm typecheck` · `pnpm lint` · `pnpm test` · `pnpm build` 통과.

## 11. 설계자가 정한 것(사용자 확인 필요)

사용자가 직접 정하지 않고 설계하면서 채운 것이다. 틀리면 고친다.

1. **계정 발급**: 메일 초대가 아니라, 권한 있는 사람이 계정을 만들고 임시 비밀번호를 직접 전달한다. 첫 로그인 때 비밀번호를 바꾸게 한다. 비밀번호를 잊으면 같은 방식으로 초기화한다. 이유: Supabase 의 기본 메일 발송은 제한이 커서 따로 메일 서버를 붙여야 하는데, 이 방식은 로그인에 메일이 필요 없다.
2. **새가족 처리 상태는 enum**(새 접수 · 연락함 · 완료). 앞서 공통코드로 말했지만, 첫 화면의 «처리 안 된 건수» 가 이 값으로 분기하므로 사용자가 정한 기준(분기하면 enum)에 따라 옮겼다.
3. **처음 넣어 둘 그룹**: «전체 관리»(잠김) · «콘텐츠 담당»(콘텐츠 5종 전체 기능) · «새가족 담당»(새가족 전체 기능). 화면에서 바꿀 수 있다.
4. **휴지통**은 메뉴를 따로 두지 않고 목록의 필터로 본다. 30일 뒤 자동으로 지운다.
5. **메뉴 옮기기 없음**: 다른 상위 메뉴로 옮기는 기능은 넣지 않는다(홈페이지 메뉴는 주소가 바뀌어서, 관리자 메뉴는 필요가 작아서).
6. **끌 수 없는 홈페이지 메뉴**: 홈이 고정 링크로 가리키는 페이지는 1차에서 끌 수 없다(6.5).
7. **알림을 받는 사람**: 따로 설정 화면을 두지 않고 «새가족» 조회 권한이 있는 사용자 전원.
8. **알림 메일에 개인정보를 싣지 않는다**(건수와 링크만).
9. **설교 시트지는 메뉴 하나**(3분류는 화면 안 필터).
10. **엑셀 다운로드는 새가족에만** 둔다. 주보 등은 내려받을 표가 없다.
11. **역할과 권한 올리기 방지**(6.4, 2026-11-23 단순화) — 그룹 만들기 · 고치기(권한 표 · 켜고 끄기)와 «전체 관리» 구성원은 «전체 관리» 만, 그 밖의 사용자 관리자는 자기가 속한 그룹에만 사람을 넣고 빼며 대상의 그룹이 모두 내 그룹일 때만 그 계정을 관리한다, 자기 그룹은 못 바꾼다, 담당 부서가 있으면 그 부서 범위 안에서만 사람을 정하고 관리한다(메뉴 켜기 · 끄기도 «전체 관리» 만).
12. **새가족 접수는 서버 전용 만능 키로 넣는다**(6.11). 방문자에게 DB 넣기 권한을 열지 않기 위해서다.
13. **분류·묶음은 등록 화면에서 바로 추가**하고, «콘텐츠 담당» 그룹에 코드 관리 권한을 준다(6.10).
14. **Storage 가 멈춘 동안 그림이 안 보이는 것은 받아들인다**(6.9). 우리 도메인을 거치는 통로는 만들지 않는다.
15. **운영 DB 변경은 수동 GitHub Actions 워크플로우**로 적용한다(6.1).

16. **한 장짜리 자리도 묶음으로 가리킨다** — 글은 `files` 를 직접 가리키지 않는다(6.3). 사용자가 정한 «공통 표 둘» 을 한 가지 방식으로만 쓰기 위해서다.
17. **부서 범위를 지금 넣는다** — 사용자에게 부서를 지정하면 그 부서(소개 글 · 담당자 · 사진)만 다룬다. 부서마다 직접 올릴 수 있어야 취합이 빨라진다(목사님 전망: 다음세대가 가장 오래 걸린다).
18. **부서 이름과 예배 요일 · 시간 · 장소는 코드에 남긴다** — 이름은 홈페이지 메뉴를 따르고, 예배 시간은 2차 «예배 시간표» 와 함께 옮긴다(6.13).
19. **부서 담당자는 부서 화면에서 따로 관리한다** — «섬기는 이들»(2차)과 같은 사람이 있어도 지금은 합치지 않는다. 2차 때 합칠지 정한다.
20. **부서 사진은 최소 한 장**, 담당자는 0명도 된다(6.13).
21. **다음세대는 메뉴 하나**(`departments`)이고 기능은 조회 · 수정 · 이력조회다 — 담당자·사진을 넣고 빼는 것도 그 부서의 «수정» 이다.
22. **홈 히어로의 대표 사진은 항상 필수**이고, 유튜브 영상은 넓은 화면에서만 · 소리 없이 재생한다. 화면 연출은 시안으로 정한다(6.12).
23. **홈 히어로는 레포에 사진 한 장을 장애 대비용으로 남긴다**(6.12) — 홈의 첫 화면이 비는 것만은 막는다. 부서 페이지에는 이런 기본값을 두지 않는다.

## 12. 사용자에게 물을 것

답을 받은 것(2026-11-17): Supabase 는 지금 개인 계정 프로젝트 → 나중에 교회 것으로(3절), 관리자가 생기면 관리자에 올리고 오픈 전에 한 번 더 가져온다(7절), 백업은 넣지 않는다(2절), 새가족 보관은 1년(6.11). 연결 값은 사용자의 메모(«성복관리자계정»)에 있다 — 운영 값은 `.env.production.local`(패키지 1 의 마지막 검증용)과 GitHub Secrets 로 옮기고, 대화·로그에 값을 찍지 않는다. 개발은 로컬 DB 값을 `.env.local` 에 둔다.

남은 것:

1. **메일을 무엇으로 보내는가** — Supabase 에 들어 있는 메일 발송은 로그인용(초대·비밀번호 재설정)뿐이고 시험용이다(프로젝트 조직 구성원에게만 가고 시간당 몇 통, 유료 요금제에서도 같다 — 구현할 때 공식 문서로 다시 확인). 새가족 알림 같은 일반 메일은 보내지 못한다. 그래서 메일 서비스를 붙여야 한다. Resend 는 보내는 주소의 도메인을 DNS 로 인증해야 다른 사람에게 보낼 수 있다(무료 하루 100통 · 월 3,000통). **목표는 Resend 다.** 2026-11-17 공개 정보 조회: `sungbok.or.kr` 의 등록인은 성복교회(등록 대행 가비아, 2031-07-15 까지), DNS 기록은 Cafe24 네임서버에 있다(기존 사이트 호스팅). 메일 기록(MX · TXT)은 지금 없다. Resend 인증에는 Cafe24 의 DNS 관리 화면에서 기록 몇 줄을 추가해야 하는데, 그 로그인은 교회가 갖고 있을 것으로 본다(사용자, 2026-11-17 — 실제 로그인은 패키지 6 전에 받아 확인한다) — 오픈 때 도메인을 Vercel 로 돌리는 데도 같은 로그인이 필요하다(ADR 0008). 보내는 코드는 한곳에 두어 발송 수단을 바꿀 수 있게 한다. **DNS 를 Cafe24 밖으로 옮겨야 할 수 있다**: Cafe24 의 DNS 는 보통 호스팅에 딸려 있어, 오픈 뒤 기존 사이트 호스팅을 해지하면 함께 없어질 수 있다(그때 Cafe24 에서 확인). 그 경우 해지 전에 가비아에서 네임서버를 가비아 DNS 로 바꾸고 기록(사이트 → Vercel, 메일)을 거기에 둔다 — 그래서 **가비아 로그인**도 필요하다. 이 전환은 관리자 범위가 아니라 오픈 작업이다. **DNS 는 가비아에 둔다(사용자 결정, 2026-11-17)** — Cloudflare 는 쓰지 않고, 공격 방어는 Vercel 기본 기능에 맡긴다.
2. **계정 발급 방식** — 메일이 붙으면 «메일 초대 + 스스로 비밀번호 재설정» 으로 한다(11절 1번을 대체). 그 전까지는 임시 비밀번호 방식으로 만든다 — 메일이 필요한 것은 패키지 C(새가족 알림)부터라 그 앞 패키지는 막히지 않는다. **진행(2026-11-23)**: «스스로 비밀번호 재설정» 화면 · 흐름은 만들어 두었다(`/admin/login/forgot` — [admin.md](../domains/admin.md) «로그인 흐름» 5번). 메일 서비스(1번)를 붙이고 대시보드 설정([deploy-and-env.md](../workflow/deploy-and-env.md) 9절)만 하면 코드 변경 없이 돈다. «메일 초대» 는 아직이다.
