# ADR 0020: 분류(카테고리)와 공통코드를 나누고, enum · 코드 값은 영문 대문자

**상태**: 채택
**날짜**: 2026-11-20

## 배경

처음 만든 `codes` 표는 콘텐츠 분류(주일광고 분류 · 앨범 분류 · 설교 시트지 묶음)만 담았는데 화면 이름이 «코드 관리» 였다. 사용자 지적(2026-11-20):

- 코드 관리와 카테고리 관리는 따로 가야 한다. 코드는 시스템 전체에서 쓰는 상태 같은 값, 프로그램을 고치지 않고 관리자가 DB 로 바꾸는 데이터다.
- 여기서 쓰는 코드가 있을 텐데 왜 비어 있는가.
- 코드 · enum 은 모두 대문자로 관리한다(DB 안에서도 소문자를 남기지 않는다).

## 결정

1. **분류(categories)** — 콘텐츠 › 분류 관리. `category_groups` · `categories`. 글은 (묶음 key, 분류 id) 로 가리킨다. 영문 값은 `slug`(공개 주소의 거르기 값이라 소문자 · `-`), 한 번 정하면 바꾸지 않는다(`guard_categories`). 처음 분류는 지금 사이트의 값(주일광고 · 부흥집회 · 교회소식 · 교회행사 · 다음세대 · 설교 시트지 묶음 9개)을 `reference.sql` 에 넣는다.
2. **공통코드(codes)** — 시스템 › 코드 관리. `code_groups`(key · 이름 · 설명 · 잠김 · 순서) · `codes`. 묶음 key · 코드 값은 **영문 대문자 · 숫자 · `_`**(`NEWCOMER_STATUS` › `NEW`).
   - 관리자가 바꾸는 값: 직분(`STAFF_ROLE` — 목사 · 전도사 · 간사). 부서 담당자의 직분은 글자 대신 이 코드를 가리킨다(`department_staff.role_id`).
   - 프로그램이 쓰는 값의 화면 이름: 콘텐츠 상태 · 새가족 구분 · 새가족 처리 상태. **잠긴 묶음**이라 코드를 더하거나 끄거나 값을 바꿀 수 없고 이름 · 순서만 바꾼다(`guard_codes`). 값은 enum 과 같다 — `supabase/tests/database/structure.test.sql` 이 둘이 같은지 잠근다.
3. **enum 값은 모두 영문 대문자**(`DRAFT` · `PUBLISHED`, `READ` · `CREATE` …, `LOWER_ELEMENTARY`). 공통코드와 같은 규칙이다. pgTAP 이 «public enum 값은 모두 대문자» 를 잠근다.
4. **공개 사이트의 타입은 그대로 소문자** — `announcements` · `sunday` · `lower-elementary` 는 주소이자 화면 key 다(`/resources/sunday`, 영상 메뉴 key). 공개 사이트가 DB 를 읽을 때(패키지 B) 읽는 자리에서 바꾼다. `enumParity.test.ts` 는 «소문자 타입의 대문자 = DB enum» 을 잠근다.
5. 메뉴 key(`users` · `categories`) · 그룹 key(`admin`) · 표 이름은 코드가 아니라 식별자라 소문자 그대로다.

## 대안

- **상태 칸을 enum 대신 코드로 바로 가리키기(FK)**: 공통코드 하나가 정본이 되지만, 권한 규칙 · 트리거 · 뷰가 모두 글자 비교로 바뀌고 값 오타를 DB 형식이 못 잡는다. enum 을 두고 잠긴 코드로 이름만 관리하는 쪽이 안전하다.
- **분류 · 코드를 한 표에**(이전 방식): 성격(공개 주소의 거르기 값 vs 프로그램 값)과 권한(콘텐츠 담당 vs 시스템)이 달라 화면 · 권한이 섞였다.

## 영향

- 변경 파일 `<시각>_admin_schema.sql` 이 enum 을 대문자로 다시 만든다(운영 DB 에는 아직 적용 전이라 데이터 옮기기는 없다).
- 관리자 코드의 권한 값이 모두 대문자다(`can(perms, 'users', 'READ')`).
- 콘텐츠 담당 그룹의 처음 권한: `codes` 대신 `categories`(조회 · 등록 · 수정).
