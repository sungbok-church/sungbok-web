# ADR 0019: DB 구조의 정본은 선언형 스키마 파일 하나, id 는 uuid v7

**상태**: 채택
**날짜**: 2026-11-19

## 배경

관리자 설계([2026-11-17-admin-design.md](../specs/2026-11-17-admin-design.md) 6.3)는 표 목록만 있고 id 형식 · 인덱스 · 권한 규칙이 정해지지 않았다. 지금 글 id 는 표마다 모양이 다르다(주보 날짜, 광고 · 시트지 «게시판-글번호», 앨범 숫자).

사용자 요청(2026-11-19):

- id 는 uuid 로, v7 이 낫지 않은가.
- 지금까지 설계한 것을 SQL 로 만들되, 여러 파일로 흩어 두지 말고 **한 곳이 정본(SSOT)** 이어야 한다.
- 조회할 때를 생각해 인덱스를 모두 걸고, 성능과 이슈를 미리 없앤다.

## 결정

### 1. 정본은 두 파일

| 파일 | 담는 것 |
|---|---|
| `supabase/schemas/schema.sql` | 구조 전부 — enum · 표 · 인덱스 · 함수 · 트리거 · 행 권한(RLS) · Storage 권한 · GRANT |
| `supabase/reference.sql` | 처음부터 있어야 하는 행 — 관리자 메뉴 · 처음 그룹과 권한 · 공통코드 묶음 · Storage 버킷 · 첫 관리자 |

- `supabase/migrations/` 의 변경 파일은 **사람이 쓰지 않는다.** `pnpm db:sync` 가 만든다.
  - 구조: Supabase CLI 의 선언형 스키마(`db schema declarative sync`, 비교 엔진 pg-delta)가 `schema.sql` 과 지금까지의 변경 이력을 비교한다.
  - 초기 행: 마지막 `<시각>_reference.sql` 과 `reference.sql` 이 다르면 그대로 옮긴 파일을 하나 더 만든다.
- 두 파일로 나눈 이유: 스키마 비교는 데이터(insert)를 다루지 않고, 스키마 파일에 insert 를 쓰면 오류다(Supabase 문서 «Known caveats»).
- `reference.sql` 은 여러 번 돌아도 같은 결과여야 하고, 화면에서 바꾼 값(메뉴 이름 · 사용 여부 · 순서, 그룹 권한)을 덮어쓰지 않는다.
- 운영 적용 절차(Actions › Apply DB migrations)는 그대로다.

**시험 결과**(2026-11-19, CLI 3.1.0):
- 표 · 인덱스 · enum 값 추가 · RLS · 트리거 · `auth.users` 트리거 · `storage.objects` 권한 · GRANT 를 잡았다.
- enum 값 추가는 CLI 가 파일을 둘로 나눴다(한 묶음 안에서 쓸 수 없는 문이라).
- 바뀐 것이 없으면 파일을 만들지 않는다.

### 2. id 는 uuid v7

- 이유: 만든 순서대로 커져 인덱스 끝에만 붙는다(v4 는 무작위라 인덱스 페이지가 쪼개진다). 정렬 · 페이지 끊기에도 쓸 수 있다.
- **Postgres 18 의 내장 `uuidv7()` 은 아직 쓸 수 없다.** Supabase 호스팅은 17 이 최신이다. 그래서 SQL 함수 `private.uuid_v7()` 을 기본값으로 쓴다.
  - 18 이 열리면(대시보드 Settings › General) 함수 본문만 바꾼다. 데이터는 그대로 둔다.
- 단점은 id 에서 만든 시각이 보인다는 것이다. 공개 주소에는 uuid 를 쓰지 않으므로 받아들인다.
- 예외:
  - 변경 이력 · 횟수 제한: 1씩 느는 숫자. 추가만 하는 표다.
  - 연결 표: 두 칸을 합친 키.
  - 공통코드 묶음: key. `reference.sql` 에서만 생긴다.
- **공개 주소는 id 와 따로 둔다.**
  - 주보: 날짜
  - 광고 · 뜰: 영상 id
  - 앨범 · 시트지: `slug`. 기존 글은 기존 번호, 새 글은 시퀀스(앨범은 1000 부터).
  - 광고 · 뜰의 기존 글번호는 `legacy_id` 에 둔다. 오픈 전 다시 가져오기가 같은 글인지 이것으로 판단한다.

### 3. 성능 · 안전 규칙(모두 `schema.sql` 머리 주석과 `supabase/tests/database` 의 검사로 잠근다)

- **인덱스는 칸마다가 아니라 조회마다 건다.**
  - 모든 외래 키 칸
  - 목록 정렬(날짜 내림차순)
  - «삭제되지 않은 것 중 유일»(부분 유일 인덱스)
  - 휴지통 정리
  - 이력: 글별 · 부모별 · 사람별, 기간은 BRIN
- **RLS**
  - 판정 함수 `private.has_permission` 하나. `(select …)` 로 감싸 쿼리당 한 번만 부른다.
  - 같은 역할 · 같은 동작에 규칙은 하나만 둔다.
  - 판정 함수 · 트리거 함수는 API 로 열리지 않는 `private` 스키마에 둔다.
- **GRANT**: Supabase 는 새 표에 방문자(anon)의 모든 권한을 붙인다(시험에서 확인). `schema.sql` 끝에서 전부 거두고 필요한 것만 준다.
- **함수는 모두 `search_path = ''`.**
- **트리거가 처리하는 것**
  - 등록 · 수정 시각과 사람(화면이 보낸 값은 무시)
  - 칸 단위 이력(새가족 개인정보는 값 대신 null)
  - 휴지통 보내기는 «삭제» 권한으로만
  - 메뉴는 이름 · 사용 여부 · 순서만 바뀜
  - 권한 올리기 방지
  - «전체 관리» 의 마지막 구성원 보호
- **설계 리뷰에서 나온 것**
  - 날짜는 `date`
  - 분류 칸은 (묶음, 코드) 두 칸 외래 키 — 다른 묶음의 코드를 막는다
  - 파일 묶음의 주인 뷰(`private.file_list_owners`) + 빠진 자리 검사
  - `profiles.email` 은 `auth.users` 를 트리거로 따라감
  - 새가족 동의 문구 판(`consent_version`)
  - 접수 횟수 제한 표(`submission_attempts`)
- **확인 명령**
  - `pnpm db:test`(pgTAP): 구조 규칙 + 방문자 · 권한 없는 계정 · 다른 부서 계정이 직접 DB 를 불렀을 때
  - `pnpm db:advisors`: Supabase 점검 도구. 경고 이상이면 실패
- **리뷰(2026-11-19)로 더한 것**
  - 그룹에 사람을 넣을 때도 «자기 권한 안의 그룹» 만
  - «등록» 권한은 아직 글에 붙지 않은 묶음에만(이미 붙은 묶음은 «수정»)
  - 글에는 그 화면의 묶음만 붙는다(`private.guard_list_menu`)
  - 자기 부서 범위는 못 푼다, 부서 slug 는 못 바꾼다(칸 단위 GRANT)
  - 엑셀 다운로드 기록의 «누가 · 언제» 는 DB 기본값(화면이 못 넣는다)
  - Storage 덮어쓰기 · 지우기에 필요한 읽기 규칙
  - 첫 관리자는 인증된 후보가 정확히 1명일 때만(2명 이상이면 적용을 멈춘다)
  - 예약 작업 · 새가족 알림 받을 사람 함수(서버 전용 키만)

## 대안

| 안 | 결과 |
|---|---|
| 변경 파일을 손으로 계속 더한다(지금까지의 방식) | 탈락 — 현재 모습을 보려면 파일 여러 개를 순서대로 읽어야 한다. 사용자가 원한 «한 곳» 이 아니다 |
| 지금 한 번 변경 파일 하나로 합치고 이후엔 손으로 더한다 | 탈락 — 오픈 뒤 첫 변경부터 다시 여러 파일이 정본이 된다 |
| id 를 uuid v4(`gen_random_uuid()`) | 탈락 — 이 규모에서는 차이가 작지만, v7 함수 하나로 얻는 것이 있고 비용이 없다 |
| 기존 글 id(날짜 · 글번호)를 그대로 기본 키 | 탈락 — 표마다 형식이 달라 이력의 «어느 행» 이 한 형식이 될 수 없고, 주소를 고치면 가리키는 곳이 깨진다 |

## 결과 · 주의

- **만든 변경 파일은 고치지 않는다.**
  - 아직 운영에 적용하지 않았으면: 지우고 정본을 고친 뒤 `pnpm db:sync` 를 다시 돌린다.
  - 적용했으면: 정본만 고쳐 새 변경 파일을 만든다.
- `schema.sql` 에 `*_list_id` 칸을 새로 만들면 `private.file_list_owners` 에도 넣는다. 빠뜨리면 `pnpm db:test` 가 실패한다.
- enum 값을 빼거나 이름을 바꾸는 것은 비교 엔진이 다루지 못할 수 있다. 그때는 만든 파일을 확인한다.
- 교회 계정 프로젝트로 옮길 때는 로그인 계정(`auth.users`)도 같은 id 로 옮긴다. 다시 만들면 `created_by` · 이력의 «누가» · 그룹 소속이 끊긴다.
