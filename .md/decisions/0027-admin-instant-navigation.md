# ADR 0027: 관리자를 Next 권장 «즉시 이동» 구조로 — nonce 없는 CSP, 미리 만든 틀 + Suspense

**상태**: 채택(2026-11-28 사용자 승인 — 1단계까지 진행)
**날짜**: 2026-11-28

## 배경

관리자 화면은 누를 때마다 서버가 화면을 통째로 그려 보낸다(ADR 0024 8번 — `admin/layout.tsx` 의 `await connection()` + `instant = false`). 그래서 데이터가 필요 없는 등록 화면도 매번 서버를 기다린다. 운영 실측(2026-11-28, 첫 응답): CDN 에 있는 공개 페이지 ~15ms · 아무 일도 하지 않는 서버 요청 ~45ms · 관리자 로그인 화면 ~110ms · 새 시트지 ~100ms — 로그인 · 권한 확인을 하는 화면과 거의 하지 않는 화면이 같다. 기다림은 확인 작업이 아니라 «서버 한 번 다녀오기 + 서버에서 화면 그리기» 다.

그동안 이 구조 안에서 기다림을 가리거나 피하는 장치를 붙였다: 브라우저가 바로 그리는 뼈대(PendingScreen · ScreenSkeleton, 화면 모양별), 배포마다 미리 받기(ScreenPrefill), 한 번 본 화면 60초 들고 있기(`staleTimes.dynamic`). 사용자 지적(2026-11-28): 땜빵처럼 진행된다 — 권장 방식으로 검토하라.

요청마다 그리게 만든 까닭은 관리자 CSP 의 nonce 하나다. Next 공식 CSP 안내: «nonce 를 쓰면 모든 페이지를 요청마다 그려야 한다», «PPR(미리 만든 틀)은 nonce CSP 와 함께 쓸 수 없다». Next 의 권장 방식(16.3 «Instant navigations» — 미리 만든 틀을 바로 보이고, 요청마다 다른 부분은 `<Suspense>` 안에서 뒤따라 채움)은 미리 만든 틀이 전제다. 같은 안내는 nonce 를 «보안 요구가 엄격하거나 · 규정상 필요할 때» 쓰라고 하고, 그렇지 않으면 nonce 없는 CSP 를 예로 든다. 사용자 결정(2026-11-28): nonce 없는 CSP 로 하고 제대로 된 방향을 정리하라.

## 결정(제안)

### 1. 관리자 CSP — nonce 를 빼고 나머지 보호는 그대로

- `script-src 'self' 'unsafe-inline'`(Next 가 화면 데이터를 인라인 스크립트로 싣는다 — 운영 홈 한 장에 인라인 35개). `'strict-dynamic'` 은 뺀다(nonce · 해시 없이 두면 모든 스크립트를 막는다).
- 그 밖의 규칙은 지금 값 그대로: `default-src 'self'` · `connect-src`(같은 출처 + Supabase) · `img-src` · `frame-src` · `worker-src` · `object-src 'none'` · `base-uri 'self'` · `form-action 'self'` · `frame-ancestors 'none'`(미리보기 틀만 `'self'`) · `upgrade-insecure-requests`.
- 지금처럼 proxy 가 `/admin` 응답마다 싣는다(미리보기 `/admin/preview` 만 틀 허용 값) — 값은 요청마다 같다. 로그인 화면으로 넘겨 보내는 응답에도 실린다. nonce 를 만들어 요청 헤더로 넘기던 일만 없앤다.
- **잃는 것**: 누가 끼워 넣은 인라인 스크립트를 CSP 가 막는 한 겹. **남는 막이**: React 가 화면에 넣는 글자를 모두 무해하게 바꾼다 — 우회하는 `dangerouslySetInnerHTML` 은 코드 전체에 0곳(2026-11-28 확인). 이 전제가 깨지지 않게 lint 로 막는다(`react/no-danger` — 관리자 · 공개 모두). 외부 스크립트 출처는 여전히 `'self'` 만이라 남의 서버 스크립트를 불러오지 못한다.

### 2. 구조 — 미리 만든 틀 + Suspense(Next 공식 «Instant navigation» 가이드)

- **`admin/layout.tsx`**: `await connection()` · `instant = false` 를 지운다.
- **`(panel)/layout.tsx`(관리자 틀)**: 로그인 정보(메뉴 항목 · 이름 · 새가족 숫자 · 비밀번호 변경 넘겨 보내기 · 접어 둔 메뉴 쿠키)를 읽으므로 `instant = false` — 처음 열 때(주소줄 · 새로 고침)는 지금처럼 기다린다. 틀은 화면을 옮겨도 다시 그리지 않으므로 관리자 안에서 옮겨 다니는 것은 각 화면의 미리 만든 틀로 즉시 보인다(Next 안내 «Disabling instant» 의 tabs 예 — 빌드 결과에서 화면 조각 `__PAGE__` 가 따로 미리 만들어짐을 확인). 처음 열 때까지 틀을 즉시 보이려면 사람마다 다른 부분을 `<Suspense>` 로 나눠야 하는데, 접어 둔 메뉴(쿠키)를 처음부터 맞게 그리는 문제가 있어 뒤로 미룬다.
- **각 화면**: 사람마다 다르지 않은 것(제목 · 등록 폼의 칸과 버튼 · 표 머리 · 검색 막대)은 틀에, 데이터를 읽는 부분(`requirePermission` + 조회)은 `<Suspense>` 안 자식으로. fallback 은 그 자리의 뼈대.
  - **등록 화면**: 폼 전체가 틀에 들어가 누르는 즉시 보인다. 고를 칸의 목록(시트지 «묶음» 등)만 뒤따라 채운다.
    - **방식(0단계 시험에서 정함, 2026-11-28)**: 폼을 `<Suspense>` 자리 표시로 두었다 진짜 폼으로 **바꿔 끼우지 않는다** — React 는 자리 표시를 한 번 보이면 0.3초는 두고 바꿔 그동안 쓸 수 없었다(운영 실측: 보임 0.02초 · 쓸 수 있음 0.32초). 진짜 폼을 처음부터 그리고, 서버에서 받을 것(사용자 · 선택지 · 날짜)은 페이지가 기다리지 않은 약속(Promise)으로 넘겨 `useArrived` 로 오는 대로 같은 폼에 채운다(손대지 않은 칸만, `dontUpdateMeta`). 권한은 받는 쪽이 `requirePermission` 으로 확인하고, 화면의 `<Suspense>` 안 `PermissionGate` 가 «없음» 을 보인다. 단계형(그룹 · 사용자)은 1단계를 바로 쓰고 2단계는 오면 보인다(그 전에는 넘어가거나 만들 수 없다). 임시 저장(`useFormDraft`)은 사용자가 온 뒤 · 서버 값을 채운 뒤 처음 켜지고, 그때 보관을 읽는다(켜진 뒤에는 계속 켜져 있다 — 리뷰에서 찾은 덮어쓰기 · 다시 읽기를 막는다).
    - **1단계 끝(2026-11-28)**: 등록 화면 7개(주보 · 주일광고 · 성복의 뜰 · 앨범 · 시트지 · 그룹 · 사용자).
  - **목록 · 상세 · 수정**: 머리 · 막대 · 칸이 즉시, 줄 · 값이 뒤따라.
- **권한**: 데이터를 읽는 자식이 `requirePermission` 을 그대로 부른다 — 데이터는 지금처럼 권한을 확인한 뒤에만 나간다. 로그인하지 않은 요청은 proxy 가 미리 만든 틀보다 먼저 로그인 화면으로 보낸다(Vercel 은 proxy 를 캐시보다 먼저 돌린다). 틀에는 사람마다 다른 값 · 비밀이 없다. 권한 없는 사람이 주소를 직접 치면 빈 틀이 잠깐 보였다가 «없음» 이 된다(상태 코드는 404 가 아니라 200 — 관리자 화면이라 받아들인다).
- 관리자 화면에 `instant = true` 를 달아 개발 중 막히는 코드를 Next 가 짚게 한다.

### 3. 링크와 미리 받기

- `partialPrefetching`(이미 켜짐) 그대로 — 화면에 보이는 링크마다가 아니라 **화면 종류마다 틀 하나**를 받아 세션 동안 들고 있는다. IntentLink(올렸을 때만) 를 보통 링크로 되돌릴지는 요청 수를 재서 정한다(2026-11-23 의 12건 · 저장마다 13건은 예전 방식 — 틀은 사람마다 다르지 않아 저장해도 다시 받을 까닭이 없다).
- 올렸을 때 내용까지(`prefetch={true}` — 쿠키를 읽는 화면은 요청 때 그려 미리 받는다)는 1차 측정 뒤 정한다.
- **2026-11-28 시험 결과 — 기본 미리 받기는 쓰지 않는다.** 링크를 기본(보이는 링크마다 틀)으로 바꾸니 화면을 열 때마다 32건 · 저장마다 29건(저장이 들고 있던 틀을 모두 버려 다시 받는다)이 나갔고, 응답은 Vercel 캐시(HIT)라 서버 함수는 돌지 않았지만 **Vercel 방화벽의 `/admin` 요청 제한(한 IP 60초 100건, deploy-and-env 7절)에 걸려 관리자가 429 로 막혔다**(측정 요청과 겹침, 곧바로 되돌림 — 7d7da69). 그래서 링크는 «올렸을 때만» 그대로 둔다: 마우스를 올렸다 누르면 틀이 즉시(새 시트지 0.02초), 바로 누르면 틀을 그때 받아 0.19초(옛 구조 0.24~0.46초). 처음 누를 때도 즉시이려면 방화벽 규칙을 바꿔야 한다(한도를 올리거나 미리 받기 요청을 빼기 — 사용자 결정 사항).
- 배포마다 미리 받기(ScreenPrefill, 37건)도 이 한도에 센다 — 한 사람이면 넉넉하지만 교회 와이파이처럼 한 IP 뒤에서 여럿이 배포 직후 동시에 열면 겹칠 수 있다. 4단계에서 필요성을 다시 본다.

### 4. 임시 장치 정리(전환을 확인한 뒤)

- 브라우저가 그리던 뼈대(PendingScreen · ScreenSkeleton) → 화면마다 Suspense fallback 으로 대체되면 지운다.
- 배포마다 미리 받기(ScreenPrefill) → 링크의 틀 미리 받기가 Vercel 의 첫 가져오기도 채우는지 재고, 그렇다면 지운다.
- `staleTimes.dynamic` 60초 → 다시 가는 화면의 내용을 즉시 보이는 데 여전히 쓸모 있으면 둔다.
- 위쪽 진행 표시줄은 둔다.

### 5. 홈페이지(공개 사이트)와 엮인 곳 — 영향 없음

- **CSP**: proxy 는 `/admin/:path*` 에서만 돈다. 공개 사이트에는 CSP 가 없어 바뀌는 것이 없다.
- **루트 레이아웃**(`src/app/layout.tsx` — html · 글꼴 · Speed Insights): 이미 미리 만든 틀이다. 그대로.
- **`cacheComponents`**: 공개 사이트가 이미 이 방식(ADR 0024)이다 — 관리자가 같은 방식에 들어오는 것이다.
- **같은 Vercel 함수**: 그대로. 공개 페이지의 서버 깨우기(AdminWarmup)도 그대로.
- **미리보기 틀**(`/admin/preview/[menu]` — 공개 화면 부품을 그린다): 부모 창이 보낸 값을 그리는 화면이라 요청 때 그려도 된다 — `instant = false` 를 그 화면에만 둔다.

### 6. 단계

0. **시험(1~2일)**: CSP 바꾸기 + 관리자 틀 + 새 시트지 · 주보 목록 두 화면만. 운영에서 «누름 → 폼이 보일 때까지» 를 재고 콘솔 CSP 위반이 없는지 본다. 기대만큼 빠르지 않으면 되돌리고 여기서 멈춘다.
1. 등록 화면 7개.
2. 목록 14개.
3. 상세 · 수정 16개 · 로그인 · 비밀번호 화면.
4. 임시 장치 정리, 문서(admin.md · ADR 0024 보충) 갱신.

## 성공 기준

- 등록 화면: 누른 뒤 폼이 보일 때까지 서버를 기다리지 않는다(브라우저가 들고 있던 틀로 즉시).
- 목록 · 상세: 틀이 즉시, 내용은 지금과 같은 시간(~0.1초) 안에.
- 운영 콘솔에 CSP 위반 0, 로그인 · 권한 · 8시간 규칙 · 미리보기 동작 그대로(테스트 + 운영 확인).

## 대안 비교

- **지금 구조 유지 + 장치 다듬기**(뼈대 늦게 띄우기 등): 작지만 원인을 두고 증상만 다룬다 — 사용자 지적. 탈락.
- **nonce 유지 + 경로마다 인라인 스크립트 해시를 뽑는 단계**: Next 공식 기능이 아니고 판이 바뀌면 깨지기 쉽다. 요청 때 그리는 부분은 미리 해시할 수 없다. 탈락(ADR 0024 보충 2026-11-28).
- **관리자 전체를 CSR(브라우저가 그리고 서버는 데이터만)**: 등록 폼은 즉시지만 관리자를 사실상 새로 짠다. 처음 여는 목록은 결국 데이터를 기다린다. Next 권장 방향(RSC)과도 멀어진다. 탈락.

## 결과 / 영향

- ADR 0024 8번(관리자는 요청마다 · nonce CSP 유지)을 대체한다 — 채택되면 0024 상태에 «8번은 0027 이 대체» 를 적는다.
- 위험: `instant` 검사 · `partialPrefetching` 은 Next 16 의 새 기능이라 판이 바뀌며 동작이 달라질 수 있다. 화면 ~40개를 손본다(단계마다 배포 · 측정).
