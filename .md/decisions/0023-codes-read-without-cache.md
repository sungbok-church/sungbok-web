# ADR 0023: 공통코드 · 분류는 캐시하지 않고 그릴 때마다 DB 에서 읽는다

**상태**: 채택
**날짜**: 2026-11-20

## 배경

ADR 0021 은 공통코드 · 분류를 서버 데이터 캐시(`unstable_cache`, 하루)에 두고 고칠 때 `updateTag` 로 지우기로 했다. 같은 날 Cache Components(`'use cache'`) 전환을 실험 · 검토하면서 다음이 드러났다(Next 16.4.5 문서 `use-cache.md` · `use-cache-remote.md` · `cacheHandlers`, Vercel 문서 runtime-cache · data-cache).

- **그냥 `'use cache'` 는 관리자 화면에서 거의 맞지 않는다.** 서버 메모리에 두는데, 서버리스(Vercel)는 요청마다 다른 인스턴스가 받을 수 있어 «요청 때 채운 값은 다음 요청까지 남지 않는 것이 보통» 이다(빌드 · 미리 그리기 때 채운 값만 남는다). 관리자 화면은 전부 요청 때 그린다(`connection()`, ADR 0024). 인스턴스가 살아 있어 맞는 경우에도 태그 지우기는 그 인스턴스 안에서만 되므로(«`revalidateTag()` on one instance does not affect others»), 다른 인스턴스는 만료 때까지 옛 이름을 보일 수 있다. 효과는 거의 없고 어긋남만 생긴다.
- **서버 사이에 공유되는 `'use cache: remote'`(Vercel Runtime Cache)도 아낄 것이 없다.** 캐시를 확인하는 것 자체가 네트워크 왕복이라, 몇 KB 짜리 표를 같은 서울 리전의 DB 에서 읽는 것과 드는 시간이 비슷하다. 대신 고칠 때 지우기 · SQL 로 직접 고쳤을 때의 늦은 반영을 신경 써야 한다.
- **과금도 이유가 되지 않는다**(2026-11-21 다시 확인). 운영에서도 Vercel 은 무료 Hobby 로 쓴다(유료는 Supabase Pro). Hobby 는 청구가 없고, 한도를 넘으면 그 기능이 최대 30일 멈춘다. 공통코드는 한 번 읽을 때 1단위(8KB)라 관리자 화면을 하루 수백 번 열어도 월 1만 단위 안팎이다 — 한도를 걱정할 양이 아니고, 나중에 Pro 로 바꾸더라도 쓴 만큼 청구되는 단가(서울 icn1: 읽기 100만 단위 $0.52 · 쓰기 100만 단위 $5.20)로 **월 1센트도 안 된다.**
- 처음 이 ADR 을 쓸 때(2026-11-20)는 «메모리 캐시는 하루 어긋남, 공유 캐시는 Pro 에서 한도 없이 과금» 을 근거로 들었다. 결정은 같지만 근거를 위와 같이 바로잡는다 — 비용이 무서워서가 아니라 **캐시해도 아끼는 것이 없어서** 뺀다.

## 결정

1. `src/shared/api/codeBook.server.ts` — `getCodeBook()` · `getCategoryBook()` 는 **캐시 없이** DB 에서 읽는다. `React.cache` 로 감싸 **한 요청 안에서만** 중복을 없앤다(요청이 끝나면 버린다 — 서버끼리 어긋날 일이 없다).
2. 쿠키 없는 읽기 전용 연결(공개 키)로 읽고, DB 오류는 던진다(빈 선택지로 조용히 그리지 않게). Supabase 설정이 없으면 빈 목록.
3. 코드 · 분류를 고치는 Server Action 은 화면만 새로 그린다(`revalidatePath`). 지울 캐시가 없으므로 `updateTag` · 캐시 태그(`CACHE_TAGS`)를 없앤다.
4. 공개 페이지가 코드 · 분류를 쓰게 되면, 캐시 없는 읽기는 미리 그리기에서 «요청 때의 빈칸» 이 된다(Cache Components, ADR 0024) — 그 페이지 쪽에서 `'use cache'` 로 감싸 HTML 에 넣거나 `<Suspense>` 안에서 요청 때 읽는다.

## 대안 비교

- **`unstable_cache` 하루(ADR 0021 그대로)**: Vercel 의 공유 저장소(Data Cache)에 두어 서버끼리 어긋나지 않지만, 만료 뒤 첫 요청은 옛 값을 받는다(사용자가 원한 «만료되면 그때 DB 읽기» 가 아님). Data Cache 는 Runtime Cache 로 합쳐지는 중이라(Hobby 는 2026-12-10) 아래 `remote` 와 같은 처지다. 탈락.
- **`'use cache'`(메모리) 하루 · 5분**: 요청 때 채운 값이 거의 남지 않아 DB 읽기가 줄지 않고, 남는 경우엔 인스턴스마다 옛 값이 섞인다. 탈락.
- **`'use cache: remote'` 하루**: 동작은 가장 정확하고 Pro 에서도 비용이 월 1센트 미만이지만, DB 를 직접 읽는 것과 비교해 아끼는 시간이 없고 지우기 관리만 늘어난다. 탈락.

## 결과 / 영향

- ADR 0021 은 대체됨. `codeCache.server.ts` 와 그 시험은 지웠다.
- 관리자 화면에서 드롭다운 · 조건이 있는 화면은 열 때마다 작은 DB 읽기를 한 번 한다(요청당 표별 한 번).
- 나중에 코드를 읽는 화면이 아주 많아져 DB 부담이 보이면, 그때 `'use cache: remote'` 를 다시 검토한다.
- 공개 페이지가 코드 · 분류를 쓰게 되면(결정 4) 페이지 쪽 `'use cache'` 안에서 읽는다 — 그 값은 미리 그린 화면(Vercel 에서는 ISR, 모든 리전이 함께 쓴다)에 들어가므로 메모리 캐시의 문제가 없다. 그때는 고치는 Server Action 이 그 페이지의 태그를 `updateTag` 로 지운다(Vercel 이 모든 리전에서 지운다).
